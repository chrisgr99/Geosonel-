# Styles: voice styles (vStyle) and rhythm styles (rStyle)

Settled in discussion with Chris, June 2026. This is the STYLE-SYSTEM
architecture — the two style types, their shared rhythm core, the app-wide
library, and the Styles tab. The auto beat-pattern GENERATION mechanics (the
constrained-weighted generator, image-as-dice, per-cycle regen, swing,
calibration knobs) live in [rhythm-auto-generation.md](rhythm-auto-generation.md);
this doc refines that one's structure where they differ (see "Divergences").

## Two style types, one shared rhythm core

There are TWO kinds of style, defined separately:

- **vStyle (voice style)** — class `VStyle` (built; `src/vStyle.js`). Pitch-forward:
  the pitched-note behaviour — scale/range/chordLock/smoothness/etc., the four
  axis drivers (pitch/velocity/duration/pan) + reserved `bend`. Character-named
  (melodic, bass, lead). Carries ONE embedded rhythm core for when it generates
  its own line's beats in Auto mode.
- **rStyle (rhythm style)** — class `RStyle` (NOT built yet). Rhythm-forward,
  percussion-capable: a **kit** (one superdough drum bank) + a list of **lanes**,
  each lane = a drum sound (bd/sd/hh/…) + ITS OWN rhythm core. Genre-named
  (Bossa, Samba, DnB, Salsa).

They **share a rhythm core** — the calibration knobs from
[rhythm-auto-generation.md](rhythm-auto-generation.md): Density, Syncopation,
Image Influence, Accent, Fills/Ratchets. A vStyle embeds one core; an rStyle has
one per lane. The sharing is NOT surfaced in the UI (no "shared core" label, no
cross-links) — the two editors simply use the SAME property names for the same
knobs, and the user recognises the kinship. That recognition is enough.

Why two types rather than one class with a melodic/percussion toggle:
- The preset libraries are genuinely different — genre rhythms (Bossa, DnB) vs
  character voices (lead, bass). Two browsable libraries match the mental model;
  one list mixing "Bossa" and "lead" reads as a category error.
- The shapes barely overlap except in the rhythm core; a toggled single class
  would leave half the form dead in each mode.
- The TYPE replaces the percussion/melodic flag for free — pick an rStyle for a
  drum object, a vStyle for a pitched line. (So VStyle's reserved `kind` field
  becomes unnecessary.)
- It leaves composition open: a *lead voice over a Bossa groove* (pick both)
  later. A toggled class can't combine two of itself.

## Lanes (percussion voicing)

A drum pattern is several instruments (kick, snare, hat, …) that must interlock —
which they can't if generated by separate objects each rolling its own dice. So
ONE rStyle owns all of them: a kit (bank) + lanes, each lane a drum sound + a
rhythm core, all generated together on a shared grid/phrase so they lock by
construction. The natural param split:

- **Shared (rStyle-level):** kit/bank, subdivision/grid, phrase shaping, Image
  Influence — everything that must align across instruments.
- **Per-lane:** the drum sound + the rest of the rhythm core (Density,
  Syncopation, Accent, Fills/Ratchets) — what makes each instrument its own part.

A vStyle is effectively the one-lane pitched case (its lane's "sound" is a pitched
instrument and its pitch is generated). The lane model could later generalise to
coherent multi-part TONAL writing (bass + comp from one object) — deferred.

## Which style drives an object's beats

Auto beat-point generation is sourced from the object's **onActiveBeat** vStyle
(or rStyle) — `onActiveBeat` is by definition the callback that fires on beat
points, so that one style does double duty: its rhythm core generates the beats,
its voice/lane fields play on them. The placeholder `autoStyle` enum
(melody/lead/bass) is REMOVED; the beat-points Style dropdown lists both
libraries (grouped Voices / Rhythms). No style assigned → fall back to the
default melodic rhythm.

Consequences (off-grid part deferred):
- Auto-rhythm only applies to the on-grid beat-point voice. The auto/rhythm
  section in an OBJECT inspector is gated on an onActiveBeat callback existing;
  for an object using only hasCollided / beenTriggered it is disabled.
- hasCollided / beenTriggered may still carry a style for NOTE behaviour, but
  those events aren't on the metric grid, so a style's rhythm-core fields would
  mean something different there — TBD, not settled.
- In the Styles TAB the rhythm section is always editable (you author a complete
  style in the abstract); the gating lives only in the object inspector.

## The Styles tab

Sidebar tab labelled **"Styles"** (not "Voices" — it holds both kinds). Three
zones, top to bottom:

1. **A Voice | Rhythm segmented control** at the top — picks which kind the rest
   of the tab edits; flipping it swaps both the list and the editor below.
2. **The named list** for that kind (New / Duplicate / Rename / Delete); built-in
   presets + the user's. Selecting one loads the editor.
3. **The editor** for the selected style — kind-specific:
   - **Voice editor:** Identity (name, instrument) · Pitch behaviour · Drivers
     (pitch/velocity/duration/pan + reserved Bend) · Rhythm (the core knobs).
   - **Rhythm editor:** Identity (name) · Kit (bank) · Groove (shared:
     subdivision, phrase, Image Influence) · Lanes (per row: drum sound + the
     per-lane core knobs; add/remove).

The kinship is visible WITHOUT being labelled: the voice editor's Rhythm band and
each rhythm lane carry identical field names.

Style names must be valid JS identifiers (so the `styles.theName` code path
autocompletes; references are dot-access, never quoted strings). The app-wide
library feeds BOTH the runtime `styles` namespace and the Script-tab autocomplete.

UI details (exact knob widgets, lane row layout, list affordances) are still TBD.

## App-wide library + persistence

Styles are app-wide, like the image gallery — define once, use across scores. A
small store module mirrors `gallery.js` (list/get/save/remove + a synchronous
in-memory cache the engine reads, since style resolution is per-note). Web: a new
IndexedDB store at a bumped DB_VERSION. Electron: a `styles` array in settings.json
via a preload bridge. The store is **type-aware** — it holds both the voice and
rhythm libraries (a type discriminator), even though only voices are populated
first. Built-ins stay code-level fallback templates (the library starts empty;
"New" can start from a built-in); resolution reads the cache then the built-ins.

## Divergences from rhythm-auto-generation.md

That doc predates these decisions; where they differ, THIS doc wins:
- It leaned toward ONE unified style (pitch + rhythm). We chose TWO types sharing
  a rhythm core.
- It put the style editor in a popover from the Style dropdown. We chose a Styles
  TAB with a Voice/Rhythm segmented control (it did foresee "a Styles area/tab").
- It had no multi-lane percussion voicing. We added the kit + lanes model.
- Its `autoStyle` submenu off the beat-points source is replaced by sourcing the
  style from the onActiveBeat slot.
Its generator, image-as-dice, per-cycle regen, Repeats-as-spatial-variation,
swing-from-onset-placement, and the five calibration knobs all stand — those are
the shared rhythm core's fields and the generation engine.

## Open questions (not yet settled)

- The rhythm-core field set is largely settled by the five knobs in
  rhythm-auto-generation.md (Density, Syncopation, Image Influence, Accent,
  Fills/Ratchets); confirm and reconcile (the earlier "metricLock" is just
  Syncopation's complement; "subdivision" is the object's beat grid, not a style
  knob — though per-lane subdivision for percussion is an open question).
- Whether `density` is a true target dial (target-density-then-distribute) or
  emergent (v0's per-slot probability).
- Image-as-dice / rhythm driver: wire now or keep canonical weights now and add
  the colour-dice as a fast-follow.
- Off-grid meaning of rhythm-core fields for hasCollided / beenTriggered.
- The tonal multi-lane (ensemble) generalisation.
