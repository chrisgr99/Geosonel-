## Section 11 — Musical Structure

This section covers how a GXW score acquires higher-level musical structure — form, repeating multi-bar phrases, per-segment tempo, meter, and harmony, which objects play when, and per-segment starting conditions for those objects — on top of the base model in which each source simply loops its own cyclePattern forever. The mechanism is a structural layer that segments the master clock into a persistent Shared baseline plus an ordered, looping list of segments, where each segment is in effect a self-contained mini-score: the score's objects in their per-segment states and at their starting positions, with a tempo, a meter, a harmonic context, and a background image, played from its defined start through a defined number of bars and then cut at the boundary as the next segment begins. Most of a segment's settings cascade from the Shared baseline — a segment holds only the values it overrides — so the structure stays compact and a one-segment score is exactly the base model with the structure invisible.

Everything in this section is subject to prototyping. The design has been worked through in conversation in enough detail to guide a first implementation, but it is provisional in a way the rest of the design doc is not, and many implementation questions of meaning and of user interface remain open (collected at the end). The right starting point is the smallest end-to-end slice — a two-segment loop that swaps which objects play and changes the chord progression, built through the existing simulation and firing engine — with per-segment tempo, per-segment image, per-segment starting conditions, and the arrangement UI layered on once the core boundary mechanism is proven.

### Why structure is a GXW-native layer

GXW owns the WHEN — the physics cursor and each source's per-source cycle clock — while Strudel owns the WHAT, the notes inside each cyclePattern. That split is exactly why higher-level structure is a real design question: nothing in the base model says "play segment A, then a varied A, then B, then repeat." Strudel's own multi-cycle constructs (`arrange`, `cat`, `<...>`) assume Strudel owns a single global timeline, which GXW deliberately took away. So song-level form is layered as a GXW-native structural clock rather than delegated to Strudel.

Conceptually the structural layer is an extension of Strudel's `arrange`. `arrange([n1, p1], [n2, p2], ...)` is a pure function of the cycle index: given a cycle it answers which segment is active and how far into it. GXW reuses that cycle-to-segment resolver as its structural clock, and extends it with the things `arrange` does not do — Shared-and-per-segment tempo, meter, object state, image, and harmony, plus per-segment starting conditions, per-segment repeat counts, and a hard re-seed at every boundary. An `arrange`-style ordered list is also a natural authoring syntax for the segment list.

### The two clocks

Adding per-segment tempo changes what the master clock is. It stops being a single uniform BPM from which everything derives and becomes a structural bar counter with a piecewise-constant tempo: the bar count advances uniformly through the piece, but the wall-clock width of a bar is whatever the current segment's BPM dictates. The structure is tracked in bars — a tempo-independent count — and the conversion to seconds is derived per segment.

This produces two layers:

- A structural layer: an ordered list of segments. By default it loops — after the final segment it returns to the first and plays forever — unless a segment is designated the last, after which playback stops. It advances in bars, knows the current segment, and at each boundary reconfigures the score-local layer below it.
- A score-local layer: everything inside a segment. This is the existing simulation, unchanged, running at the segment's BPM with each object in its segment state and at that segment's starting conditions.

A time signature (beats per bar plus the beat unit, e.g. 4/4) supplies the bar-to-beats conversion that makes "a segment is N bars" precise. Like BPM, the time signature cascades: the Shared baseline carries a default meter, any segment may override it, and a blank segment field inherits the Shared default. A piece can therefore run in 3/4 in one segment and 4/4 in others; a per-segment meter change is handled at the boundary exactly like a tempo change.

### The fixed object set

The set of objects is fixed at the score level. Segments never add or remove objects; they only change an object's state — active, passive, or disabled — and override some of its properties. Adding or removing an object is always a Shared-level action. An object that should sound only in the bridge exists in the shared object set and is simply active in the bridge segment and disabled everywhere else.

This simplification removes a whole class of complexity: there is no per-segment identity set, no reconciling which objects exist where, and no question of what an override on a nonexistent object means. The inspector's object list is constant across segments, so switching segments never adds or drops objects on the canvas — it only changes their state, greying the disabled ones — and the cascade below always has a base object present to inherit from. Nothing is ever hidden from the canvas: a disabled object stays visible but greyed, so there is no "hidden object" state to reason about.

### Object states: active, passive, and disabled

An object is in one of three states, and the state cascades from Shared like any other field. Active is the normal state: the object's cursor is present, so it collides and fires, it shows in full colour, and it moves. Passive removes the object's cursor. Because the cursor is both the collider and the firing element, a passive object makes no sound of its own and is not a collider, but it stays full colour and keeps moving, and it can still be a target — another object's cursor can cross it and run its beenHit. Hence "passive": it reacts but does not act. Passive applies only to cursor-bearing objects, which is curves and sprites; a trigger has no cursor and is inherently target-only, so a trigger cannot be made passive — it can only be disabled. Disabled is full inactivity on any object type: the whole object is greyed, frozen if it animates, and out of collisions as both collider and target, with no firing. A disabled object is how a segment drops a member, and because membership is just the disabled flag resolved through the cascade, disabling an object on Shared removes it everywhere that does not re-enable it.

The visuals follow the states with nothing ever hidden: active is normal, passive is full colour minus the cursor, and disabled is greyed. Greying is reserved for disabled — a change from the current build, where a muted sprite or trigger desaturates to grey; under this model a passive object keeps its colour and only its cursor goes away. This retires two older ideas: the per-object "mute" becomes "passive" (the word "hide" leaves the object vocabulary entirely), and the curve-only `hide` field and any hide-inactive segment flag are dropped, since a disabled object is always shown greyed rather than removed from the canvas.

### Segment properties

A segment carries, on top of the values it inherits from the Shared baseline:

- Length in bars.
- BPM. The segment sets the transport tempo for its duration; the Shared default BPM applies to any segment that does not override it.
- Time signature. The meter for the segment, cascading like BPM — the Shared baseline holds the default, a segment may override it, and a blank segment field inherits.
- Repeat count: how many times the segment plays before the arrangement advances to the next segment (default 1). Each repeat re-seeds the segment from its starting conditions, so the iterations are identical — a compact alternative to placing the same segment in the list several times. Repeat count is genuinely per-segment, not a cascading field; it is arrangement structure.
- Last-segment flag: marks the segment after which playback stops, once that segment has finished its repeats. At most one segment carries it. If no segment is flagged, the arrangement loops back to the first segment and plays forever, so the flag is how looping is controlled: a finite piece has a last segment, an endless one does not. A single-segment score flagged last plays its repeat count and stops; the same segment left unflagged loops forever, its repeat count then having no effect since the loop subsumes it. The flag normally sits on the final segment in order; placed earlier it simply ends the play-through there, which is mostly useful as a temporary ending while authoring. Like name and repeat count, the last-segment flag is arrangement structure and is not cascaded.
- Object states: which objects are active, passive, or disabled in the segment, as described above. This is not a separate membership list — an object's membership is its disabled flag resolved through the cascade, so disabling it on Shared drops it from every segment that does not re-enable it, and disabling it on one segment drops it only there.
- Optional background image. Cascades like the other defaults — Shared holds the score's image, a segment may override it. Because the image is the scalar field that drives sprite forces and feeds the pattern signals through OKLCh sampling, swapping it per segment changes the physics landscape and the signal source the segment reads from, not just the backdrop.
- Key and chord progression: the segment's scale/key and its chord progression, each cascading independently from Shared (described under Harmony below) — a segment can inherit both, override just the key, just the progression, or both.
- Per-segment starting conditions for its objects, described below.

### Harmony: key and chord progression

A score's harmony lives in two independent, cascading properties: the key — the tonal centre and scale the music is written in — and the chord progression. Both sit on the Shared baseline and cascade to segments exactly as tempo does: a segment inherits Shared's key and progression unless it overrides one or both, so it can recolour an inherited progression by changing only the key, replace the progression while keeping the key, or change both. This reverses an earlier per-segment-only decision. Harmony was first made per-segment to escape the rigidity of a single score-wide key — the way GeoSonix fixed harmony at the score level — but once Shared exists as an off-arrangement baseline that everything inherits, the cascade is a superset of both: the set-the-key-once convenience and full per-segment freedom in one mechanism. So this is the model catching up to a capability that did not exist when the per-segment call was made, not an arbitrary reversal.

The key is a plain field — a tonal centre and a scale name. The chord progression is Strudel mini-notation whose tokens are scale degrees relative to the key, with one cycle mapping to one bar; for example `<1 [5 4] 6>` is a I chord across the first bar, a V then a IV for two beats each in the second, and a vi in the third, and a progression shorter than the segment loops to fill it. Because the degrees are relative to the key, changing the key repositions or recolours the whole progression. The degrees resolve to concrete pitches through @strudel/tonal, and per-object patterns read the effective harmony through `mapNotesTo` and the harmony-context signals (`currentChord`, `currentScale`, `currentTonic`, `currentRoot`) described in Section 10.

The progression is authored as a labelled block in the Code tab and promoted with Cmd-Enter, the same way an object's cyclePattern is authored, so it inherits the editor's mini-notation display including the active-token boxes — the sounding chord lights up, an accessibility win. The Shared baseline's progression is the block labelled `$chords`; a segment overrides it with a segment-scoped block named `$chords@<segmentname>`, for example `$chords@verse`. This `@scope` suffix is the first concrete use of the segment-scoped labelled-block convention this section anticipates. The key, by contrast, is a plain inspector field rather than a labelled block; only the progression is authored as code.

### Per-segment starting conditions and the editing model

A segment owns the starting conditions of the objects active in it. Move an object, resize it, change its colour, or change its state while a given segment is shown, and those become that segment's initial state, leaving every other segment untouched. A verse and a chorus can hold the same lead instrument at different positions and sizes while remaining the same object. For a score with a single segment this reduces exactly to the current model; the structure is one conceptual level deeper only when more than one segment exists.

The layer being edited is either the Shared baseline or a specific segment, and which one is selected is the entire edit-routing control. While a score has only one segment, Shared stays hidden and the author simply edits that segment; edits land on the Shared baseline, so a segment appended or inserted later inherits the developed setup and starts with an empty override layer of its own. Once a second segment exists, Shared becomes a visible, separately-editable layer: editing a segment writes a segment-local override and never touches Shared, while editing Shared changes the baseline and flows to every segment that has not overridden that field. The split happens at the first divergence, whether a segment is appended or inserted in front — develop the body as the only segment, then add an intro, and Shared surfaces while the body keeps its music by continuing to inherit it. One rough edge is accepted for the minimal version: a Shared edit will not move a field a segment has already overridden — override wins — and that is invisible until the later orange inherited-versus-overridden cue.

The selector is the inspector's segment dropdown, described under Transport and position display, which lists Shared at the top alongside the named segments. Selecting Shared shows and edits the shared base values; selecting a segment shows the effective values (Shared merged with that segment's overrides) and routes edits to that segment's override layer. While the transport is stopped, selecting a segment pins it for editing and the canvas shows that segment's starting state — its objects in their segment states and at their segment-start positions, its image.

The edit-routing rule is therefore: Properties-tab edits apply to the layer selected in the inspector dropdown (Shared or a segment), Score-tab edits are score-wide or live on a segment's own card. The canvas obeys the same rule — dragging an object while a segment is shown sets that segment's position override; dragging under Shared sets the shared default.

### The cascade and the override UI

The storage model is a cascade. Each object is defined once at the Shared baseline — its identity, its callbacks, its default fields and pattern — and each segment carries only a sparse set of overrides, the fields that differ there. The effective value in a segment is the base merged with that segment's overrides; an absent override means inherit. One segment with no overrides is again exactly today. This is the same inherit-or-override idiom GXW already uses for per-object harmony (`HARMONY_OVERRIDE_FIELDS`), applied one level up. The private-copy alternative — a full scene per segment — was considered and set aside: it duplicates shared state, loses object identity across segments, and is painful to migrate away from, whereas the cascade collapses to the copy model's simplicity whenever a segment overrides every field.

A later inspector phase makes the cascade legible per field with a single accent colour, orange, distinct from the green used for active field frames so the two systems never collide. A field that is overrideable but currently inherited shows its label in orange. A field that is overridden in the shown segment shows an orange box around its label, or an orange underline if a box reads too cramped at zoom (both are trivial to render; the underline is the lighter option). A field that is not overrideable carries no orange at all, in the normal label colour, so the presence of orange means "part of the override system" and the box-or-underline means "overridden here." The inspector is a purely visual surface — the author does not use Speak Selection on form data — so colour alone is an acceptable carrier here. Clicking an orange label toggles the override on and off; the toggle is non-destructive, retaining the value rather than discarding it, so the click is an A/B compare between the Shared value and the segment value, while a deliberate "forget this override" is a separate, rarer action so an accidental click never wipes a value.

This per-field override cue is later-phase polish — the inspector's Phase 7 build-out, confirmed against a real form at zoom. The Phase 1 model is the cascade itself: the Shared baseline plus sparse segment overrides, with the effective-value read. The orange visuals arrive once the inspector is built out; until then inherited-versus-overridden is simply not shown per field.

### What is overrideable

The object ID is the only field that is never overrideable. The callbacks (the hasHit, beenHit, and onTick function-name slots) and the cyclePattern are shared for now: they are authored in the Code tab and behaviours.js rather than in the inspector form, so per-segment variants of them would mean segment-scoped code, which is a larger feature. This is a "for now," not a dead end — segment-scoped labelled blocks (`$lead@bridge: ...`) could add per-segment patterns without disturbing the model, and the chord progression's `$chords@<segment>` block is the first realized instance of exactly that convention. Everything else — position, velocity, size, colour, the object's state (active/passive/disabled), voice, per-object harmony override, the key, and the chord progression — is overrideable.

### Different material across segments

Because the pattern is not overrideable per segment, different melodic material in different segments does not come from one object playing different notes per segment; it comes from activating different objects. The verse lead and the chorus lead are separate objects in the fixed object set, each with its own shared pattern, and the segment's state decides which is live. Harmonic variation is the other half: a single shared pattern that reads the effective harmony (through @strudel/tonal or the harmony-context signals) produces different pitches as the chords change, which covers a chord progression directly. So the working idiom is "different notes by harmony, different material by membership": a twelve-bar blues is mostly a chord progression — shared, or overridden per segment — feeding shared leads, and a pop AABA bridge is a bridge object active only in the bridge segment.

### Segment boundaries: the mini-score model

The structural clock is authoritative. When a segment's bar length elapses, the boundary fires regardless of where any object is in its own cycle: an object mid-sweep is interrupted and moved to the start of the next segment (or to the start of the same segment, if a repeat remains). At a boundary the controller, in one step:

1. Switches the transport BPM, and the time signature if the next segment overrides it, to the next segment's values. A meter change is handled exactly like a tempo change.
2. Swaps object state: applies each object's resolved active/passive/disabled state for the next segment — restoring cursors to the now-active objects, removing them from the passive ones, and greying and freezing the disabled ones. This writes through to the same per-object state the inspector and the canvas tool use, not a parallel one, so the last write wins and manual changes coexist.
3. Swaps the background image if the next segment's effective image differs, recomputing the OKLCh buffer and pixel-sampling array so sprite forces and pattern signals read the new field.
4. Re-seeds the next segment's active objects to their segment-start home — that segment's authored starting conditions, base merged with overrides — via the full reset that rewind performs: cursor t, sprite position and velocity, curve runtime offset and velocity, cycle counter, the wall-bounce flip signs, the per-sprite RNG seed, and the procedural audio-fire throttle.
5. Updates the harmonic context to the segment's effective key and chord progression.
6. Zeroes the segment-local clock.

A repeat of a segment is the same boundary with steps 1, 2, 3, and 5 unchanged: only the re-seed and the clock-zero apply, since the BPM, meter, object state, image, and harmony all stay the same. That is exactly why a repeat produces an identical iteration. Inside a segment nothing new happens: each active object loops its own cyclePattern at its own beatsPerCycle against the segment's BPM, exactly as today. The segment is a self-contained run between two hard cuts.

### Procedural callbacks loop for free

Because the boundary re-seed restores precisely the dynamic state that rewind restores, and because onTick, beenHit, and hasHit are pure side effects of that state that never mutate the deterministic motion (Section 9), a segment's procedural music replays identically on every repeat: the tenth play of a segment produces the same notes, hits, and forces as the first. This is the payoff of treating a segment as a mini-score rewound to its beginning.

The "for free" is real but conditional: it holds only if the boundary applies the complete per-object reset, not a partial one. A reset that restored cursor and position but carried over a sprite's RNG state or its audio-fire throttle would let the repeats drift. The existing `_rewind` already enumerates the full set of fields to reset; the segment boundary applies that same reset scoped to the segment's active objects, with the segment's starting conditions as the target rather than a single global home.

### Why per-segment tempo is tractable

Changing tempo mid-piece would normally mean carrying every object's cursor phase across a tempo discontinuity, which is awkward — the simulation's existing mid-play BPM handling recomputes phase via the closed-form `computeCyclePhaseFromGlobalTime` against `_simTime` as if the new tempo had applied since time zero, which is a phase jump that is correct for a live tweak but wrong for a musical segment boundary. The hard re-seed removes the problem entirely. Each segment runs at a constant BPM from a known start state, so there is never a phase to carry across the discontinuity. The interrupt-to-start behaviour the form already wants and the per-segment tempo are the same mechanism: a boundary that stops, retunes, re-seeds, and resumes.

A segment's wall-clock duration is therefore `bars × beatsPerBar × 60 / BPM` per iteration; with a repeat count the segment occupies that many bars times the repeat count on the structural timeline.

### Determinism and scrubbing

The segment schedule — lengths, tempos, meters, repeat counts, object states, images, key and chord progression, starting conditions — is authored, fixed data. An object's state within a segment iteration is a pure function of its segment-start conditions, the time elapsed into the current iteration, and the segment's BPM. The current segment, repeat index, and bar-offset for any elapsed time come from a closed-form segment resolver that walks the segment durations (each segment contributing repeat-count times its bar length), the same closed-form move the simulation already uses one level down for cycle phase. The arrangement has a finite total length when a last segment is designated, and otherwise the resolver wraps modulo the segment list. So rewind, scrub-to-arbitrary-position, and faster-than-realtime offline render all remain deterministic; determinism now reads as "(segment schedule, elapsed time) gives the events."

### The Score tab

Score-wide state has had no real inspector surface; tempo, meter, key, output, and now the segment list live in the JSON tab or nowhere. A new Score tab is the home for it. A small score-global header holds only the output routing — the engine (MIDI or Superdough) and its target — because everything else that used to read as score-wide is now a cascading default carried on the Shared row: bars, BPM, time signature, key, chord progression, and image.

Below the header the arrangement is an always-visible vertical stack of compact cards — Shared pinned at the top, then each segment in playing order. There is no collapse or expand: a card is only about three or four lines, laid out GeoSonix-style with several fields per line, so a number of segments fit in the inspector at once without scrolling, which is what makes collapsing unnecessary and keeps drag-reorder workable under zoom. Cards reorder by dragging or by a per-card up/down control pair; Shared has no slot in the running order and is not reorderable, so dragging applies to the real segments only.

The Shared card is a reduced segment card: it holds only the cascading defaults — bars, BPM, time signature, key, chord progression, and image — with no name, repeats, last-segment flag, or membership, since those are arrangement structure the baseline does not have. Its first line reads "Shared" plus bars and BPM (and time signature). A segment card carries the segment's own settings: the first line is the name, bars, BPM, time signature, repeat count, and a marker when the last-segment flag is set; the remaining lines hold the segment's key, a reference to its chord-progression labelled block (the way the object inspector refers to a cyclePattern), an optional background image, and three compact, clickable counts — how many objects are active, passive, and disabled in the segment. The two card shapes are deliberately not identical.

There is no per-object list on the card. The canvas is the source of truth for which specific objects are active, passive, or disabled: read the state off the canvas, and edit an object by selecting it there, which routes the edit to the pinned segment. The three counts are the bridge between card and canvas — clicking a count selects that whole category on the canvas (a multi-select reusing the existing select-all/multi-select), so clicking "active" surfaces every active object at once. The per-object starting conditions of those objects — position, size, colour, velocity, voice, per-object harmony override — live on the objects themselves, set by selecting the segment and then editing in Properties or dragging on the canvas.

Membership and the passive/disabled state are set in two ways, with no keyboard shortcut for either — the old Cmd-Shift-M mute shortcut retires, consistent with how other object properties have none. The first is the Properties fields for a selected object. The second is a single canvas tool following GXW's existing one-shot/double-click-to-lock pattern, which cycles the clicked object's state for the currently selected layer: curves and sprites rotate active → passive → disabled → active, and triggers, having no cursor, toggle enabled ↔ disabled. One tool covers every state, and disable is the per-segment membership control applied per object on the canvas rather than ticked off a per-card list. Reusing a segment elsewhere in the arrangement is copy-and-paste, covered under Reuse and reprises below.

The vertical-list shape is deliberate for the zoom workflow: segments stacked, each compact, is all single-axis scrolling, with no grid to lose one's bearings in when magnified. An object-by-segment matrix was considered and rejected as a primary surface for that reason. This also draws the inspector's dividing line: per-object state on Properties and the canvas (routed to the shown layer), score-wide and segment-level state on the Score tab, with the JSON tab the fallback for anything not yet surfaced.

### Segment lifecycle

A fresh score auto-creates exactly one segment, with Shared hidden behind it as described above; segments are the basic unit, not an advanced add-on. The last remaining segment cannot be deleted, since a score always has at least one. Deleting a segment that is currently pinned or looped falls back to a neighbour — or to Shared, if Shared was the target. Deleting from two segments down to one collapses the survivor into Shared: the survivor's overrides flatten onto the Shared baseline, its override layer empties, and the score returns to the clean one-segment mode with Shared hidden again and edits landing on Shared. This is the symmetric inverse of the split that surfaced Shared when the second segment was added, so no invisible overrides are ever left behind.

### Reuse and reprises

The arrangement is an ordered list of self-contained segments, and recurring material is reused by value: a reprise is an independent copy of a segment, not a linked alias. Copying a segment carries its field values and overrides at the moment of the copy, and nothing links the two afterward, so they are edited separately from then on. This fits how reprises actually behave in music — the recurring A in an AABA or AABAC form is rarely identical on its return; the final A resolves differently and the C is new material — so copy-then-vary is the common case, and strict edit-once-update-all identity is the narrower one.

AABAC is the worked example. The arrangement is the ordered list A (repeat count 2), B, an independent copy of A, then C: the adjacent AA comes from A's repeat count, and the non-adjacent return comes from the copy. The copy and the original A share nothing once the copy is made, so tweaking the reprise — a different ending, a thinned texture — touches only the copy and leaves the first A alone.

An alias model — segment definitions plus an arrangement of references to them, with edit-once-update-all identity — was considered and deferred as a possible future upgrade. Staying by value keeps the first data-model commit's schema a simple ordered list of self-contained segments; the reference model can layer on later if strict shared identity turns out to be wanted.

The copying mechanism is a Score-tab action that arrives with the inspector UI phase, not the first data-model commit. It reuses the canvas clipboard idiom already used for objects: select a segment card, Copy, select the card the reprise should follow, and Paste drops an independent copy after the selected card. Paste-after-selected-card was chosen over duplicate-then-drag because it needs no long drag under zoom, and it inherits the clipboard's cross-score support, so a segment can be lifted from another score. The pasted copy is fully independent: it gets a new auto-suffixed but editable name, its `$chords@<name>` progression block is duplicated to `$chords@<newname>`, and the last-segment flag is not carried over.

### Transport and position display

With per-segment tempo, the transport's elapsed readout naturally refers to the current segment, so the display splits into two levels. The transport readout becomes in-segment position: beats and measures (and seconds) into the current segment iteration at its tempo. The overall position is carried by the dropdowns, of which there are two, with an intentional asymmetry. The transport-bar dropdown is the playback-position readout and segment navigator: it lists only the real, playable segments, since Shared never takes a slot in the arrangement — the one exception is that it displays "Shared" while Shared is the current loop target (see Loop-segment mode). The inspector dropdown is the editing-layer selector and lists Shared plus every segment, because Shared is a layer you edit but never hear in the normal progression.

The two dropdowns mirror each other on the real segments: choosing a segment in either selects it in both, bidirectionally. Shared is reached only through the inspector. During normal playback the transport auto-advances through the segments as its position readout, while the inspector holds the segment it was pinned to rather than chasing the music, so stopping returns the author to the segment they were editing. Editing while listening is served by loop mode below, which is why normal full-arrangement playback need not move the editing target. Keeping the inspector dropdown pinned and visible — a sticky header — means the editing layer stays in view while working down the form under zoom; the dropdown is itself the "which layer am I editing" indicator, so no separate label is needed.

A scrub bar can still be added later for finer overall-position feedback, laying the segment list out end to end with a position marker. One layout choice would then be open: by bars (each segment's width proportional to its bar count times its repeats, tempo-independent, reading like a score) or by wall-clock seconds (a slow segment wider, reflecting real playback time); bars is the working preference. The two-level display supersedes the deferred elapsed-time-display rework, since a real time signature makes the bar-and-measure framing honest.

### Loop-segment mode

A toggle — a small push button marked with a loop sign, in the inspector or toolbar, using GXW's one-shot/double-click-to-lock pattern — switches playback from progressing through the arrangement to looping a single segment, giving continuous audio while editing. The loop follows a real segment, the transport's current one; selecting Shared in the inspector while looping changes only what you edit, not what loops, so you can hold a segment looping while toggling the inspector between that segment and its Shared baseline — the back-and-forth between auditioning a segment and adjusting the baseline it inherits. Shared is itself solo-loopable: loop it on its own to audition the baseline every segment inherits, and while it is the loop target the transport displays "Shared." For Shared to be loopable it carries its own bars and BPM, which are also the cascade defaults segments inherit.

Each loop pass re-enters the segment boundary — the full re-seed plus audio flush — so an edit to the segment or to Shared is heard on the next pass, and the loop point is a clean hard restart rather than a seamless join. Loop mode is ephemeral monitoring state, not saved into the score, and it ignores the segment's authored repeat count; the loop unit is one pass of the segment's bars (provisional — the better choice between this and honouring the repeat count will only be clear in use). Turning the loop off while on Shared jumps to the first segment and continues the arrangement, since Shared has no slot in the running order. The button can be designed now, but the looping behaviour itself depends on the structural clock and the hard-cut boundary engine, which arrive in a later build phase.

### Relationship to the conductor mechanism

An earlier version of this section specified a `conductor()` pattern: a curve whose cyclePattern tokens are commands rather than notes, with a `role` field for group addressing and a command vocabulary (rewind, mutate, chord-change tokens, solo) dispatched to the targeted objects. The segment model absorbs the conductor's two largest jobs. Form gating by solo becomes per-segment object state; chord-change tokens become the cascading key and chord progression. What remains potentially useful from the conductor idea is the per-event, in-musical-time command channel for things that are not "select state for a span" — a `mutate` applied to a voice at a beat, project-specific verbs registered through a `defineCommand` registry in behaviours.js, and the timeline-on-canvas visualization of a conductor curve. Whether that channel survives alongside segments, layers within a segment, or is retired is open. The `role` field is likely to persist regardless, since it is a natural way for a segment to name a group of objects to address.

### Open questions

Several questions from the original design are now settled by the Phase 1 decisions and are noted here as resolved; the rest remain genuinely open.

- Repeat semantics (settled). A repeat re-seeds the segment so iterations are identical — the working choice, since a non-re-seeding repeat would be indistinguishable from a longer segment. Loop-versus-stop is handled by the last-segment flag: the arrangement loops by default and terminates at the designated last segment.
- Editing layer follow-versus-pin (settled). During normal playback the inspector holds its pinned segment while the transport advances; editing while listening is served by loop mode instead. The two dropdowns mirror on the real segments, and Shared is reached only through the inspector.
- Per-segment time signature (settled). The meter cascades like BPM — a Shared default with an optional per-segment override that inherits when blank — rather than being fixed once per score.
- Key and chord progression (settled). Both cascade from Shared as two independent fields, with a segment free to override either or both; the per-segment override of the progression is the segment-scoped labelled block `$chords@<segment>`. Still open within this: the exact degree-token grammar and how far it extends toward the full Strudel/Tonal chord vocabulary (v1 starts with diatonic chords named by scale degree), and how a segment's effective harmony composes with the per-object harmony overrides and `mapNotesTo`.
- Membership expression (settled). Per-segment membership is the disabled flag resolved through the cascade, set per object via the canvas cycling tool or the Properties fields — not a role-based activation expression or a separate active list. The `role` field may still persist as a naming convenience for addressing a group of objects.
- Reuse model (settled). Recurring material is reused by value — a reprise is an independent copy of a segment, not a linked alias — copied through the Score tab with paste-after-selected-card. The by-reference alias model is deferred as a possible future upgrade.
- Override UI (deferred to a later phase). The orange-label scheme (orange label overrideable, orange box-or-underline overridden, no orange shared) and the non-destructive click-toggle are inspector polish to confirm against a real form at zoom; box versus underline is an aesthetic call. The Phase 1 model is the cascade itself.
- The overrideable field set. Working answer: everything except ID, with callbacks and cyclePattern shared for now; per-segment patterns may follow later via more segment-scoped labelled blocks, of which the chord progression's `$chords@<segment>` is the first.
- Loop unit. One pass of the segment's bars, ignoring the authored repeat count, is the provisional choice; whether to honour the repeat count instead will be clearer in use.
- Carry-through is deferred. Boundaries are uniformly hard-cut: every active object re-seeds to its segment-start conditions, so each segment stays self-contained and the segment list reorders, duplicates, and deletes freely. Carry-through — letting a sustained drone or pad glide across a boundary instead of restarting — is a nice-to-have left for later, because expressing it as "carry from the previous segment" couples a segment to its predecessor and breaks under reordering: the carried fields, and which fields are greyed in the inspector, would depend on what now precedes the segment, and an object set to carry could end up first in the order with nothing to carry from. The order-safe way to add it later is a whole-arrangement per-object flag — "this object runs continuously and is never re-seeded at boundaries" — set once on the object rather than per adjacency, so reordering cannot break it and the affected kinematic fields are simply not segment-overrideable for that object. Less flexible than per-boundary carry, but it matches the real use case (an element that sounds throughout) and keeps the boundary model uniform. In the meantime the author can approximate carry-through by authoring an object's starting conditions in the next segment to match where it left off; for a sustained pad or drone the slight re-articulation at the boundary is usually unobtrusive, so deferring carry-through does not block the effect, only the engine guarantee of it.
- Image preload at the boundary, so the swap and OKLCh recompute do not hitch, and how that interacts with scrubbing to an arbitrary segment.
- Audio scheduler boundary barrier: the one-cycle-ahead scheduling must flush events pre-scheduled past a boundary at the old tempo and re-bootstrap at the new BPM, extending the existing BPM-change flush as a planned structural event.
- Fate of the conductor channel: whether the per-event command channel (mutate, defineCommand verbs, the conductor-curve visualization) survives alongside segments, and if so at what level.
- Scrub-bar layout, if added: by bars or by wall-clock seconds.
- Mutate semantics, if the command channel survives: what a mutation does to a voice, whether mutations accumulate or reset, and the default when none is configured.

These open questions are tracked here rather than in TODO.md until they are resolved; they are pre-implementable design work, not pending implementation items.
